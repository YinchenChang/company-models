# MiniMax v0.2 分段建置：共同規則（2026-10-22，chat 端）

適用 M1–M3。開工前必讀：本檔、該張工作單、規格 `minimax/docs/plan/20261022_MiniMax_v0.2_規格.md`、`minimax/README.md`、v0.1 報告與 Tokenomics 連接審視報告（`minimax/docs/reports/`）、進度檔（M1 建立：`minimax/docs/reports/20261022_minimax_進度.md`；M2 若先開工且進度檔不存在，自行建立同名檔）。
衝突時的優先順序：**該張工作單 > 本檔 > 規格 > repo 根目錄 README > minimax/CLAUDE.md（M1 建立後）**。

## 1. 分段、續接、分支
- 每張工作單一個分支、一個 PR（base `main`），分支名寫在各工作單。每完成一個步驟：更新進度檔 → commit → push。額度或時間快用完時，先 commit＋push＋進度檔寫明「下一步」再結束。
- PR 用 REST（`gh api`），GraphQL 不可用。推送前 `git fetch origin main`；淺層 clone 遇 HTTP 413 先 fetch 再推。
- **不得合併任何 PR、不得 force push、不得改 `main`、不得刪除分支或歷史。** 只改 `minimax/` 與 `.github/workflows/minimax-*.yml`（M1）、repo 根目錄 README 的 MiniMax 一列。
- 預估每段 ≤2 小時；實際超過 4 小時停下，交 chat 端。超過 2 分鐘的命令背景執行，但**必須等跑完、看到結果再回報**。

## 2. 資料紀律
- 每筆數字：數值、低、高、單位、期間、來源（文件名＋網址）、文件日期、擷取日、標記（Verified／Interested-party／Analogy／Assumed／Derived／Decision）、一手／二手、利害方與誘因（Interested-party 必填）。Analogy／Assumed 一律給區間。
- 分層：公司財務原始數據→`SRC_MM`；算力物理與產業資料→只取 Tokenomics（官方快照），不重算；假設→`Inputs`；Tokenomics 沒有的算力資料→「Tokenomics 缺口」。
- **不得杜撰數字**；「找不到」與「不存在」分開寫，寫明試過哪些來源。報導互相矛盾時全部登錄。
- SemiAnalysis（含 InferenceX）不可單獨引用。同一來源的多個轉載不算獨立交叉驗證。
- **不以公司自己的目標或預測反推參數**；公司數字只作對照列（v0.1 的 η 校準與 2025 營收校準不在此限）。
- **不得在任何對外請求（含 HTTP User-Agent）中使用使用者 email**；SEC／HKEX 等網站需 User-Agent 時用通用字串（例如 `research-bot`）。
- 不得嘗試 `dangerouslyDisableSandbox` 或其他繞過權限的做法；環境錯誤先診斷，無法解決即回報。
