## 1. 這一輪做了什麼

過去 Siliconomics 的基準＝原始顆數 × S33 係數（2028 ×0.8、2029 ×0.85），係數是一個 [Assumed] 的假設。規則 v1.1 改成：**先看每一年兩層各自有沒有證據，再決定誰定基準**，不看數值高低。這次把這套判斷做成活頁簿裡看得見的結構：

1. **In 頁新增 M30 協調區塊（藍字，皆標來源）**：每年的 Wattonomics 換算值（需求側讀數）、兩層證據比例、`cov_done`（Wattonomics 覆蓋是否補齊）、門檻與緩衝區、上次判定（首次留空）。換算值與 Wattonomics 證據比例都標「暫值，待 Wattonomics v0.3.2 後重算」。
2. **新增 Coord 頁**，一列一步：供給側讀數 → 現行取法 → 需求側讀數 → 兩層是否有證據（含緩衝區）→ 狀態甲乙丙 → 由誰定基準 → 是否改用換算值 → 是否對帳中 → 該年標示 → 依規則的基準 → 基準係數 `crd_k`。
3. **基準鏈改讀 `crd_k`**：Units、Deploy、Mkt（HBM）係數列、ABF、Rack、Equip、Cap 原本乘 S33 係數的地方，一律改乘 `crd_k`。`crd_k` 在「維持現行」的年份就等於原本的 S33 係數（所以 cov_done＝0 時數字完全不變）；在「改用換算值」的年份＝換算值 ÷ 原始顆數讀數，S33 就不在基準鏈上了，只留作情境參照（J5：情境 A＝供給側讀數）。
4. **Interface 新增 E 節**，讓下游讀得到兩個讀數與狀態（見第 2 節）。
5. **狀態檔**：`siliconomics/tools/export_baseline_status.py` 產生 `siliconomics/data/baseline_status.json`，供 `tools/baseline_coordination/check.py` 檢查。

## 6. 待 Project 判斷

1. **對帳單與期限**：四年都「對帳中」，規則要求登錄對帳單與診斷期限（C6 第 3 點「下一個財報季結束」）。對帳單是 Drive 的哪一份、期限是 2026-11-30 還是 2027-02-28，規則沒寫死；`builder/seed/coord_meta_v0.19.json` 留空。
2. **基準改變要不要傳到下游自己算的量**：本庫內部的基準鏈都已跟著 `crd_k`，但 cov_done＝1 時 **NVIDIA 模型不跟隨**（重建結果與 cov_done＝0 逐格相同）——NVIDIA 等約 50 個個股建檔程式與 `markets/memory/market.py` 直接讀 In 頁 `um28_B`／`um29_B` 自行乘出基準。要讓規則基準到達個股，需改讀 `SIF_UnitsCoef_Base`（＝`crd_k`）或新增 In 頁層的 `crd_k` 輸出；這屬步驟 5a／5b 的範圍，本輪未改。
3. **各平台等比例**：改用換算值時，本試作把換算值 ÷ 原始顆數當成一個係數，所有平台（NVIDIA、ASIC、AMD）等比例縮放，延續 S33 的做法。規則沒寫平台間怎麼分配（規則 v1.1 也把「證據比例分區塊」列為以後）。
4. **2027 供給側讀數的口徑**：v0.18 已把 2027 顆數依 HBM 供給截頂（× 0.9404，決策 S48）寫進 In 頁，所以供給側讀數 2027＝39.16（截頂後），不是截頂前的 41.65。依步驟 3 橋接表的口徑沿用截頂後；「2027 是否截在 HBM 上限」規則第 8 節列為待 Andy。
5. **甲狀態的處理**：試作只做「甲且殘差超出 ±15%（rc_tol）→ 對帳中，基準維持現行」；規則的「證據等級高者為準」需要逐年證據等級，目前沒有輸入欄位。2026 在 NVIDIA FY27Q3（11-19）公布後 Siliconomics 證據可能到約 65%，會由乙變甲，屆時需要這一段。
6. **狀態改變的生效時點**：規則寫「狀態改變的年份，基準在下一次該層升版時改，改前標對帳中」。試作沒有記錄「上次狀態」，只有上次是否有證據（緩衝區用）；需不需要再加一欄「上次狀態」由 Project 決定。
7. **檢查程式的小問題（不在本分支修）**：`check.py` 第 6 項以集合交集比對 `years` 的字串鍵與 `depends_on_years` 的年份，若年份寫成整數就永遠不命中、靜默跳過。本試作把年份寫成字串讓它生效；建議 `check.py` 或 README 寫明型別。另第 7 項（② 時差庫存累計）需要 `timing_cum`，本庫沒算不含覆蓋的換算值，未提供。
8. **R4 橋接、Recon 快照與全下游 cascade**：本輪沒有重跑（cov_done＝0 下輸入不變）。cov_done＝1 合併前需重跑 R4（`SIF_GWvsWT_Base`、`SIF_CapOnlineGW_Base` 才會更新）與全部下游。
