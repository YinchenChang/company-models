## 1. 為什麼分段
Nebius 曾因額度用完遺失整輪建置。規則：**每完成一個步驟就 commit 並 push，同時覆寫進度檔**；任何時候中斷，下一個代理都能從進度檔接手。

## 2. 分支、PR、合併
- 每張工作單一個分支、一個 PR（base `main`）。分支名寫在各工作單。開工第一步：從最新 `main` 開分支、push、開 draft PR（REST：`gh api repos/YinchenChang/company-models/pulls -f title=... -f head=... -f base=main -f body=... -F draft=true`；GraphQL 不可用）。
- **代理不得合併、不得 force push、不得改 `main`、不得刪除分支或歷史。** 合併由 chat 端審查後執行。
- 推送前先 `git fetch origin main`；淺層 clone 推送若遇 HTTP 413，先 fetch 再推。
- 指令一律在 `openai/` 內執行；不得改動 `nebius/` 或其他公司資料夾。

## 3. 進度檔（接手用，必做）
- 路徑：`openai/docs/reports/20261007_openai_進度.md`（各張共用；每張開工時新增自己的段落，不刪其他段落）。
- 最上方「目前狀態」每次 push 前覆寫三項：**已完成**（含 commit）／**下一步**（具體到下一個代理可直接動手）／**未解問題**。
- 下方各段「步驟紀錄」表：步驟｜狀態｜commit｜備註。
- 每個步驟完成 → 更新進度檔 → commit → push，三件事一起做。
- 察覺額度或時間快用完：立即停止新工作，先 commit、更新進度檔（寫清楚做到哪、下一步），push 後結束。

## 4. 資料紀律（同 Nebius 共同規則第 4 節，另加本模型規則）
- 每筆數字：數值、單位、期間、來源（文件名＋網址）、文件日期、擷取日、標記（Verified／Interested-party／Analogy／Assumed／Derived）。Analogy／Assumed 一律給區間。
- 分層（CLAUDE.md 第 1 節）：公司財務原始數據→`SRC_OAI`；算力相關的產業與物理資料→只取 Tokenomics 名稱（`TK_Link`），本模型不重算；假設→`Inputs`。Tokenomics 沒有、但屬算力相關的資料：不在本模型自建，列入報告「Tokenomics 缺口」。
- **不得杜撰數字**；「找不到」與「不存在」分開寫，寫明試過哪些來源。
- SemiAnalysis（含 InferenceX）不可單獨引用，須第二個獨立來源。
- **不以公司自己的目標或預測反推參數**（例如以管理層 2030 營收目標回推單價或 GW）。正向由 Tokenomics、物理產能與可觀察市場資料推導，公司數字只作對照列（反向模式 R1–R3 是對照用的獨立區塊，不回饋基準）。r6 已核准的 V2（η 以 2025 實際推論支出校準）不在此限。
- 公式不含常數（E6）；穩定 ID（SRC_OAI_nnn、INP_nnn、Checks Cnn）只增不重用；Excel 優先（藍字由 Excel 擁有）。

## 5. 判斷類事項
- 依序：該張工作單的預設 → r6 第 2 節 → 最保守且最常見的口徑。
- 每一項在報告「已套用的預設」列出：問題｜採用的預設｜替代選項｜對結果的影響方向（能量化就量化，例如對 2030 每 GW 差額的影響）。
- 範圍：只做 r6 P2–P5 與各張工作單所列；不新增 r6 未列的機制（例如 Anthropic 競爭、價格戰情境）——想到的列入報告「建議後續」。

## 6. 停止條件（只有這些才停下；其餘照預設做完）
1. `YinchenChang/company-models` 無法推送，或 Tokenomics 無法讀取。
2. 同一項 parity 或重算錯誤經三次實質不同的修正仍失敗，且原因是工具或模板結構限制。
3. 要讓模型成立，必須改動 Tokenomics（本 repo 不得改 Tokenomics；列入「Tokenomics 缺口」即可，除非缺口使該段核心輸出無法計算）。
4. 需要改 `main`、force push、刪除分支或歷史。
停下時：commit 並 push 現況、進度檔「未解問題」寫明卡在哪與建議，在 PR 留言（第一行 `[OpenAI 回報] Sn｜停止｜YYYY-MM-DD`），然後結束。
