## Z3 審查後追加 Z3b（chat 端，2026-10-08；η≫1 的處理）
審查結論：η＝38–49 主因是「token ÷ 參考請求組合的每 GW 產能」把快取命中的輸入 token 當成與參考組合同等的算力工作量；程式碼代理流量以快取命中為主，每 token 算力約為解碼的千分之一。Tokenomics 已有逐 token 類型的單位成本（物理推導），應改用它換算，而不是以 η 吸收。

| 項 | 改動 | 理由 |
|---|---|---|
| F1 | **token GW 改依 token 類型加權**：Demand 各來源（API 按量、Coding Plan、免費、C 端）的 token 拆成新鮮輸入／快取命中輸入／輸出（API 沿用既有 `cache_hit`、`out_share`；Coding Plan 新增 Inputs：快取命中占比 Analogy 0.9（0.8–0.97）、輸出占比 Analogy 0.03（0.01–0.08），依據 Z1-R 與程式碼代理公開統計，寫明）；每類 token × TK `IF_CostPre_*`／`IF_CostCache_*`／`IF_CostDec_*`（Hopper 欄，層級對應 D24r；國產與 H20 × 產出比之倒數）＝所需推論持有成本 → ÷（TK `IF_HoldEcon` Hopper × 持有比 × 匯率）＝token GW。成本口徑（100% 或基準利用率）須與 `IF_HoldEcon` 一致，報告寫明。TK_Link 新增這些具名範圍（讀 Tokenomics Interface，不重算），`check_tk_snapshot.py` 同步 | 算力物理一律取自 Tokenomics；類型加權是物理事實，不是擬合 |
| F2 | η 重新校準（2025、1H26）。逐年路徑：若校準 η ≤ 1 → 同 OpenAI（線性回升至 2030＝1）；若 η > 1 → 基準沿用 1H26 值、情境「收斂至 1」並列，報告解釋 η>1 的殘差可能來源（研發算力費含雲端部署服務、Tokenomics 參考組合差異） | η>1 時「回升至 1」不是保守而是無依據的效率衰退 |
| F3 | 舊法（參考組合 token ÷ IF_TokGW）保留為對照列，不進計算鏈 | 可追溯 |
| F4 | 2H26 起供給機制（依需求配置、研發占比沿用 1H26 實際 0.70）接受為預設，列入報告「chat 端審查確認」 | 規格未規定，代理補上合理 |
