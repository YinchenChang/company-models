## 一、結論

1. **稽核的數字屬實：3,023 個**（公式共 21,099 個，占 14.3%）。第三方稽核與本次獨立點數完全一致。這個數字也是 `wattonomics/tools/check.py` 每次執行都印出的提示（「3023 個公式格值為空（空字串結果或未重算；若全部為空表示未經 LibreOffice 重算）」）；該句把兩種原因併在一起，容易被讀成「未重算」。建議下次工程升版把提示拆成「空字串結果 N 格」與「缺快取 M 格」兩個數（本張不改，避免動到 check.py 的輸出格式）。
2. **全部是合理的空字串結果，沒有未重算、沒有斷鏈。**
   - **未重算：0。** 3,023 格在檔案 XML 內都是「公式 ＋ 空字串結果」（`t="str"`、`<v/>`），不是缺快取。另以 LibreOffice 對整本活頁簿強制重算（78,485 格逐格比對），快取與重算結果不同的格數：**0**。
   - **斷鏈：0。** 含 `#REF!` 的公式 0、壞掉的具名範圍 0、快取中的錯誤值 0。
   - **合理性：** 2,358 格（78%）由程式逐格驗證（前提格確為空、已知值鏈鏈尾、直接引用空字串來源、護欄條件為真）；其餘 665 格屬標記欄、常數占位、查表無資料等公式家族，以家族為單位判斷（未逐格評估，清單中標「家族判斷」）。
3. 所以第三方稽核「公式存在但快取值為空」的說法在事實上成立，但風險判斷不成立：這些是模型刻意用 `""` 表示「這個年份或玩家沒有資料」，不是壞掉的公式。
4. **不修任何公式。** 沒有發現「明顯工程缺陷」需要處理。

## 三、為什麼會有這麼多空字串（白話）

模型的年份欄固定是 2023–2032 十欄，但每個玩家、每個項目不是每年都有資料。公式的寫法統一為「沒有輸入就回空字串」，而不是寫 0，這與規則 C0 第 7 點「沒有證據不得歸零」的精神一致（本報告不確認這是原設計意圖，只確認結果行為如此）。大宗來源：Players 頁各玩家的「輸入、晶片換算、已知值、前一／下一已知值」輔助列（728）、Gap（579）、Funding（556）的查表與標記列、C1（343）與 CapexGW（325）的個股模型財年資料缺年。

## 四、觀察（不修；供下次升版參考）

- 141 格是常數公式 `=""`（Players 無晶片資料的列與首年「年平均」、Deploy 年增率與年平均的前段年份等）。功能上等同空白格，但仍計為公式；整列公式統一是刻意的結構選擇。
- Gap 頁 2 格（`E175`、`F175`）含 `IF(FALSE(),"",…)`，條件恆為假，是 builder 產生式的殘留死分支。結果值正確，不影響任何數字。若要清理，應在下一次改 builder 的單獨工程 PR 處理。
- CapexGW 另有 3 格（`E247`、`E257`、`E263`）寫成 `IF(2024>=2026, …, IF(Players!…="","",…))`：年份寫成字面常數，條件恆為假，只走後段；同樣是 builder 逐年展開的產物，結果正確。
- 外部程式用 openpyxl（`data_only=True`）讀取時，這 3,023 格會得到 `None` 而不是 `""`。其中 Interface 頁的 309 格在 `export_snapshot.py` 匯出的快照裡就是 309 個值為 `null` 的名稱（`WIF_Funding_*` 178、`WIF_Gap_*` 116、`WIF_PlayerGW_*` 15，皆為該年份無資料；快照共 2,647 個名稱）。下游若直接讀這些名稱要先處理 null；這屬各下游的讀取規則，不是模型缺陷。

## 五、驗證了什麼、沒驗證什麼

- 驗證：公式數與空快取數（openpyxl 兩種讀法）；XML 型態；強制重算零差異；斷鏈零；2,358 格逐格合理性。
- 沒驗證：665 格的合理性只到公式家族層級；沒有用 Excel 本體重算（只用 LibreOffice）；Excel 與 LibreOffice 對 `"" + 數字` 的處理一致（皆為 #VALUE!），而活頁簿沒有任何錯誤值，故不影響。
