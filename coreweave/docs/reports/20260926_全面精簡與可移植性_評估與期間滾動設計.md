## 1. 敏感度與矩陣：方案 A 與折衷方案 C

### 1.1 實測（2026-09-26，LibreOffice 24.2，透過 UNO 操作本模型的 Excel）

| 項目 | 結果 |
|---|---|
| 全部重算一次 | 0.02–0.04 秒 |
| 快照法：改一個輸入 → 重算 → 讀目標價 | 每次約 5 毫秒；89 個情況約 0.5 秒，三情境約 1.5 秒 |
| 活表法：90 列全模型模擬運算表（LibreOffice 內部形式 `TABLE()`） | 重算時間增加約 0.1 秒 |
| 數值 | 穩態 EBITDA 率 59%／70% 時目標價 $38.3155／$60.6718。快照法、活表法與 JS 引擎三者一致（到小數第 4 位） |
| 反向 DCF 以 Python 求解的估計 | 24 次二分法反解 × 約 40 次重算 × 5 毫秒 ≈ 5 秒 |

→ 兩種方法在 LibreOffice 都很快；Excel 對 2,000 個公式的模型重算 90 次，也在一秒內可以完成。**效能不是決定因素。**

### 1.2 Andy 提出的兩項結構限制

**(a) 輸入格與運算表須在同一工作表（勿改 6）。**
可以不放在「輸入與假設」：在運算表所在的分頁放一個「覆寫格」（預設空白），模型改讀「有效值＝覆寫格空白時用輸入頁的值，否則用覆寫格」。運算表變動的是覆寫格，所以可以和運算表放在同一頁（例如評價頁）。藍字輸入格仍是常數，不會變成公式。

代價：模型中所有讀取該輸入的公式，都要改成讀「有效值」。

**(b) fix_datatable.py 的擴充需求，比原先說的還多一項。**
- 目前只支援「單變數、輸入值排成一欄」。
- 目前也只支援**每個工作表一張**運算表：程式把整頁的 `TABLE()` 當成一個矩形，第二張表會直接報錯。
- 雙變數矩陣要另外支援 `dt2D`（兩個輸入格）。
- 「0.4x 債務上限」那張股權矩陣其實有三個變數（折價、股權上限，再加上固定為 0.4x 的債務上限）。一張運算表只能變動兩個輸入格，所以一定要用「情況編號」編碼。這正是 Andy 擔心的做法；用覆寫格可以避免把藍字輸入改成公式，但編號本身無法避免。

### 1.3 比較

| | A：全部活的（模擬運算表） | C：評價矩陣活的、資金面快照 |
|---|---|---|
| 敏感性排名（13 變數 × 高／低） | 覆寫層：13 個輸入改經「有效值」，其中 7 個是逐年向量，需新增倍數或加減格；再加 26 列單變數表 | Python 逐一改輸入、重算、寫值。不動模型公式 |
| EBITDA 率 × 債務上限（6 格） | 雙變數表（需擴充 dt2D） | 快照 |
| 折價 × 股權上限（兩張，32 格；含 0.4x） | 情況編號＋單變數表（或兩張雙變數表加編碼） | 快照 |
| WACC × g（25 格） | 雙變數表 | 雙變數表（相同） |
| 錨定 × 倍數（40 格） | 已有，Excel 直接公式 | 已有 |
| fix_datatable.py | 擴充：每頁多張、dt2D、驗證 | 擴充：dt2D（評價頁只有一張，「每頁一張」的限制不受影響） |
| 無法在本環境驗證的 Excel 結構（需 Andy 用 Excel 開檔確認） | 3 種：每頁多張、dt2D、情況編號 | 1 種：dt2D |
| 動到核心模型公式 | 約 16 個輸入的所有引用處（風險最高；以 JS 敏感性結果逐項核對可發現錯誤） | 只有 WACC、g 兩處改讀有效值 |
| 在 Excel 改輸入後 | 全部自動更新 | 評價矩陣會更新；快照不會更新，另加一格「快照是否與目前輸入一致」，不一致時顯示「快照已過期」 |
| 新增程式 | 覆寫層、fix_datatable 擴充 | Python UNO 驅動（反向 DCF 本來就需要，共用）、快照區、過期檢查、fix_datatable 的 dt2D |
| 工作量（相對） | 大：約 2–3 輪 | 中：約 1–1.5 輪（UNO 驅動算在反向 DCF 內） |
| 放置位置 | 敏感性排名、兩張資金矩陣和覆寫格需要同一頁：新增「評價_敏感度」頁（+1 頁）或放評價頁底部（約 +100 列）。WACC × g 放評價頁 | 快照全部放在「評價_反向DCF」頁，改名「評價_反向DCF與敏感度（快照）」：第一屏只放反向 DCF 三個數字與敏感性前 7 名，其餘收合。WACC × g 放評價頁 DCF 段下方收合。分頁數不變 |
| 對精簡的影響 | 多一頁或約 100 列，另有一層覆寫格要解釋 | 快照集中在一頁、預設收合；「輸入與假設」不增加 |
| 5b 匯出 | 3 情境各重算一次，運算表隨之更新 | 建置時每情境各算一次快照（共約 1.5 秒） |

**建議 C**，理由如下：
1. 核心模型公式幾乎不動，純結構驗收（數字不變）的風險最低。
2. 快照值仍由 Excel 公式算出（Python 只負責改輸入與讀值），不違反「Excel 為唯一計算引擎」。
3. 需要 Andy 用 Excel 實機確認的新結構只有 1 種。
4. 與反向 DCF 的做法一致，讀者只需理解一種「快照」。

之後如果要升級成全部活的，敏感性清單已放在 company.json（見下），可以改用 A，不必重做。

**不論選 A 或 C 都要做**：敏感性排名的變數清單與高低幅度（例如穩態 EBITDA 率 59%／70%、建置成本 ±20%），目前寫死在 JS（`sensitivities`），5a 移到 `company.json` → `methodology.sensitivities`。

## 2. 期間滾動設計（草案；B 階段實作）

### 2.1 設計基準
| 公司 | 財年結束 | 目前首期 | 備註 |
|---|---|---|---|
| CoreWeave | 12 月 | 1H 實際＋2H 模型（Q3 10-Q 後：9M 實際＋Q4 模型） | |
| Nebius | 12 月 | 同上 | |
| Oracle | 5 月 31 日（FY27＝2026/6–2027/5） | Q1 實際＋Q2–Q4 模型 | |
| OpenAI | 日曆年（未上市） | 可能只有全年模型 | 實際數多來自報導 |

### 2.2 company.json 新增 `calendar`
| 欄位 | 意義 | CoreWeave 目前 | Oracle 例 |
|---|---|---|---|
| `fiscalYearEndMonth` | 財年結束月份 | 12 | 5 |
| `latestQuarterReported` | 最新已公布季度（財報新聞稿）→ 驅動季度層 | FY26Q2 | FY27Q1 |
| `latestQuarterFiled` | 最新已申報季度（10-Q／10-K）→ 驅動年度首期 | FY26Q2 | FY27Q1 |
| `modelYears` | 首期之後的完整財年數（見待決 2） | 4 | 4 |

由此自動推算：
- **評價日**＝`latestQuarterFiled` 的季末（目前 2026-06-30）。
- **首期**＝該財年剩餘季度的模型部分，長度 0.25／0.5／0.75／1 年（首期長度＝剩餘季數 ÷ 4）；沒有已申報季度（OpenAI）或剛申報完 Q4 時，首期為下一財年的全年模型（長度 1）。
- **期間標籤**依財年產生（CoreWeave「FY26」…；Oracle「FY27」…，FY27＝2026/6–2027/5）。首期的模型部分標為「2H26」「Q4 FY26」「Q2–Q4 FY27」等。
- **季度標籤**依財年產生（Oracle 為「FY27 Q2」，不用日曆季）。

`actual1H` 改為通用的 `ytdActual`（年初至今實際）：
- `throughQuarter`（例如 FY26Q2）、`months`（6）。
- 欄位與現在相同（現金、營收、CapEx、利息、租金支付、償債、借款、股權…）。
- 沒有實際數時整段為 null，畫面顯示「不適用」。
- 標籤「1H26 實際」改為由此產生（「9M26 實際」「Q1 FY27 實際」）。

### 2.3 折現與目標價時點改用日期
- **DCF**：現行的 UFCF 已是「評價日到各期期末」（首期 0.5、FY27 1.5…），股權募資 PV 是「期初到位」。改為由日期推算，**以月計**（期末都是月底，月數除以 12）。
  - 目前的日期推算結果與現值完全相同（6 個月＝0.5），所以可以用「數字不變」驗收。
  - 若改用實際天數，會變成 184／365.25＝0.5038，數字會小幅變動，所以不採。
- **JS 引擎與 Excel 需要改的計算處**：DCF 折現期數（`n + .5`）、終值時點（4.5）、選擇權期限（4.5）、股權 PV（`r − .5`）、EV/EBITDA 腿「折回 FY27 末」的年數、RPO 桶按月分攤的起點、既有債務與租賃到期表的歸期、EBITDA 率爬升的起點。
- **目標價時點**（現為「FY27 末」）要有滾動規則，見待決 3。

### 2.4 Comps（同業）改為 LTM／NTM
- 每家同業在 company.json 加 `fiscalYearEndMonth`。
- **LTM**：最近 4 個已公布季度合計，標明截止季。
- **NTM**：未來 12 個月共識；只有年度共識時，依財年剩餘月數加權兩個財年（日曆化：NTM＝FY1 × 剩餘月數/12＋FY2 × (1 − 剩餘月數/12)）。
- CRWV 自身的 NTM 可以直接取季度層未來 4 季的模型值。
- 缺資料時顯示「不適用」，不以不同期間並列。
- 現況：NBIS 的 EBITDA 用 FY2025、營收用 TTM，期間本來就不一致，備註已註明。**同業的季度數與 NTM 共識需由 Andy 查證後提供（不得自行補數字）**，見待決 4。

### 2.5 共識檔年度標籤
共識資料檔保持只讀。在 company.json 加 `meta.consensusYearBasis`：
- `fiscal`：共識的「2027」＝公司 FY27，Oracle 即為 2027 年 5 月結束的財年。
- `calendar`：需要日曆化。
- 建置時依此把共識年度對應到模型期間；對不上時建置失敗，不猜。
- 「全年口徑」（年初至今實際＋首期模型）的比較方式沿用 v4.3，只是把 1H 一般化為 YTD。

### 2.6 每季滾動的操作流程（寫進交接檔）
1. **財報當天（新聞稿）**：填 `quarterly.actuals`，`latestQuarterReported` 加一季，焦點季改為下一季。年度首期不動。升版。
2. **10-Q／10-K 申報後**：填 `ytdActual`（Andy 提供），以及新的 RPO 桶、債務到期表、租賃到期表；`latestQuarterFiled` 加一季 → 首期自動縮短一季、評價日後移、目標價更新。升版。
3. **財年最後一季（10-K）後**：首期變為下一財年的全年模型。若選「模型期長度固定」（待決 2），需要補新一年的假設（MW 路徑、每 MW 收入與成本、租金等），由 Andy 決定。

### 2.7 測試
暫存的虛構 company.json（不入 repo）涵蓋：12 月財年（首期 0.25／0.5／0.75／1）、5 月財年（Q1 實際＋Q2–Q4）、無實際數（OpenAI 型）。檢查期間與標籤、折現期數、季度加總＝年度，以及「不適用」的顯示。

## 3. Q3 滾動與 5a 的銜接

### 3.1 確認：季度層在財報當天更新，年度首期在 10-Q 後滾動
**同意。** 年度首期的資金欄位（現金、利息、租金支付、償債、借款、股權、capped call、JV、營運現金流、預付）以 10-Q 的現金流量表為準；新聞稿只夠填季度層。季度層中新聞稿或法說沒有揭露的指標，也等 10-Q 再補。第 2.2 節的兩個進度欄位就是依這個分工設計的。

### 3.2 兩條路
依 handoff，Q3 10-Q 預計 11/16 前申報。

| | 路徑 1：在 main 的 v4.4 上先把首期改為「9M 實際＋Q4 模型」 | 路徑 2：等 5a 合併後，以通用機制滾動 |
|---|---|---|
| 註 | Andy 說的「首期 0.75 年」是實際部分；模型部分會變成 0.25 年（periodYears 第一格 0.5 → 0.25） | |
| 要改的地方 | Excel 與 JS **兩套引擎**都要改（v4.4 仍是雙引擎，cmp31 要一致）：計算處約 20 個（JS 約 10、Excel 約 10），寫死的「1H」「6/30」「2H26」「0.5」出現處約 280 處（build_xlsx 約 140、JS 約 140；粗估，含重疊），加上 cmp31 的標籤 | 5a 本來就要做的通用機制，額外工作只有 10-Q 資料更新 |
| 資料 | 10-Q 的 9M 資金欄位、9/30 RPO 桶、債務與租賃到期表（Andy 提供） | 相同 |
| 工作量 | 約 2–3 輪，而且全部會被 5a 取代（拋棄式） | 0（包含在 5a） |
| 風險 | 高。「半年」的假設散在各處且有隱含用法（FY26 全年＝1H＋2H 的比較、CapEx 下限、JV「2026 年內履行」、FY26 利息＝1H＋2H 等），容易漏改；main 與 5a 分支同時大改 build_xlsx，合併衝突大 | 時程：5a 在 10-Q 之前未合併的話，年度首期多停留在 6/30 基準一季（約 6–7 週），目標價晚一季更新；季度層不受影響 |

**建議路徑 2**，並調整 5a 的順序：B 階段第一項就做期間滾動，目標在 10-Q（約 11/16）前合併 5a。

**另一個限制（兩條路都有）**：5b 之前 HTML 仍用 JS 引擎，而 JS 也寫死半年首期。所以 5a 的期間滾動必須同時改 JS 的計算處（約 10 處，第 2.3 節所列），cmp31 才能在滾動後仍然一致。這屬於「維持運作所需的最小修改」。

HTML 中寫死期間或日期的文字（約 140 處，粗估；多在資金模型頁與次層的連動檢查敘述）在 5b 前不搬。滾動後這些文字會停留在 6/30 的敘述，需要 Andy 接受；頁首、期間標籤等主畫面文字會改由期間標籤產生。

**備案**：如果 11/9 時 5a 的其他部分（精簡、敏感度、非區間型指引）還沒完成，把期間滾動拆成獨立 PR 先合併（需要 Andy 同意例外，因為守則是一個任務一個 PR）。
